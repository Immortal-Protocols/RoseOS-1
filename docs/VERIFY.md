# Verifying a RoseOS build

Each step yields one kind of evidence; one kind never stands in for another.

| Kind | Proves | Does not prove |
| --- | --- | --- |
| `source-inspection` | What a revision declares (manifest, routing, pins) | Built or shipped bytes |
| `artifact-inspection` | Signed/published bytes: checksums, signatures, candidate, image contents, APK identity | Boot, rendering, behavior |
| `runtime-readonly` | A booted guest's properties, installed bytes/versions, HOME resolution | What the screen shows |
| `runtime-interactive` | Launch paths, screenshots, UI dumps, transitions on that guest | A physical phone or another OS product |
| `screenshot-comparison` | Heuristic match with the candidate's Home reference (wallpaper or Oxblood field raster) plus a side-by-side image | Visual acceptance (a person reviews it) |
| Physical acceptance | Owner-run checks on the actual phone | Anything beyond that phone and build |

Tool: `scripts/rose-verify.py` (offline except `runtime`; JSON out; exit 0 ok,
1 check failed, 2 invalid input, 4 setup missing). `unavailable` means not
measured, never a pass. Every result carries `method`. `expected` prints the
repository pins.

## Candidate expectations (`--expect`)

A build is checked against one explicit file of its exact identities, never
another build's pins and never a loosened pin. `runtime` and
`release --extract-apps` require it; `apk` without it compares nothing.

- **Schema** (docstring of `rose-verify.py`): `label`, `channel`, `candidate`
  (full SHA), `target`, `apps` (`package`, `version`, `sha256`, `imagePath` for
  extraction), `appSignerSha256`, `basis`; optional `build`,
  `avbPublicKeySha256`, `home` (`hifi-wallpaper` or `oxblood`: the reference
  the candidate's Home implements; an expectation without it is compared with
  the wallpaper, as every build before #410 draws it). With `home`, `apk`
  also checks that `OxbloodField` is compiled in exactly when `home` is
  `oxblood`.
- **Fail-closed:** unknown keys, nulls, short hashes, non-integer versions,
  repeated packages and empty app lists exit 2. An unlisted package, a missing
  `imagePath`, a device other than `target.device`, or a differing candidate or
  build fails.
- **Files** (`qa/verification/expectations/`, copies of existing pins; tests
  fail on drift): `beta-frankel-2026102804.json`; `alpha-40719075730.json`
  (historical: that build failed, no image); `app-rose-agent-304.json`
  (app-only, from Infra's receipt).
- **New candidates** get their own file from Infra's actual receipt, never from
  source, a planned version or another build. The existing alpha image's
  expectation is generated by `scripts/alpha-runtime.py` (C).

## A. Artifact inspection (any agent, no device)

1. **Download** one fresh copy through the public read mode
   (`github.com/Immortal-Protocols/pixel-ota/releases/download/<tag>/<asset>`)
   into a new directory outside the repo. If denied, stop and report; never
   switch to the API, a push attachment or private artifacts.
2. **Check:**

   ```sh
   python3 -I scripts/rose-verify.py release DIR --expect EXPECTATION.json \
     --extract-apps /scratch/x --partition product --partition system_ext \
     --partition vendor --partition system --receipt /scratch/release.json
   ```

   It checks present files against `SHA256SUMS`, the listed AVB key, the
   candidate and build in `verification.json`, the feed line, and the OTA
   `pre-device` against `target.device`. Extraction decodes each partition from
   `payload.bin` (every operation and partition hash checked; full OTAs only),
   reads ext4/erofs without mounting, and records `build.prop`
   target/API/ABI, each expected APK (package, version, SDK, ABIs, HOME and
   launcher activities, full signer, bytes), Rose Agent's wallpaper and
   Home/conversation classes, and every packaged HOME candidate (the device
   decides the holder). About 5 GB scratch; delete afterwards.

`apk APK... [--expect FILE]` inspects loose APKs; a local rebuild fails the
byte and signer checks by design.

## B. Source inspection (no build)

`rose-verify.py source SHA` reads the Rose Agent manifest and `MainActivity`
routing (pages, HOME rule, presence target, pairing redirect, wallpaper hash).
It says what a revision declares, not what a device runs.

## C. Alpha runtime on Cuttlefish (lead-owned, explicit handback)

- **Handback:** an explicit serialized handback from Chief or the Infra lead,
  naming guest and window, recorded verbatim in `--handback`. No concurrent VM
  change, new resource, credential or route.
- **Image and expectation:** the lead supplies the `emulator-alpha-export` run,
  artifact digest and `alpha-export.json` SHA-256 (images verified by run
  40777816699: compile 40765631053, BUILD_DATETIME 1793220134, product
  `ae9cfd4d`, apps 302/4/28, super.img `e543c130…`; 40765631053 wrote no build
  receipt). `python3 scripts/alpha-runtime.py expectation --artifact-dir D
  --export-receipt-sha256 S --out E` writes the measured expectation. It is the
  2804-era alpha: no Agent 308, PR70 or PR85 claim. `.github/workflows/alpha-runtime.yml`
  does all of this on a fresh instance once Infra sets
  `ROSEOS_ALPHA_RUNTIME_READY`; its run id is the handback.
- **Read-only:** `rose-verify.py runtime --serial S --handback REF --expect E
  --out DIR [--user N]`. One tested user (default: the current user; an
  unknown or unreadable one stops the run) is bound to every observation:
  `pm path`, the dumpsys `User U:` state, device-wide versionCodes and SYSTEM
  flag, on-device APK hash, HOME role holders, the **unqualified** MAIN/HOME
  resolution, and the PR70 marker `rose_home_role_selected` (read only). Other
  users are `unavailable`. No input, launch or write.
- **Interactive** (`--interactive`, inside the window, foreground user only):
  system HOME key (passes only on Rose Home); explicit Rose HOME (labeled; never
  offsets step 1); Open Rose → `RoseConversationActivity`; Back → Rose Home;
  launcher-icon entry (recorded, version-dependent); HOME again. Screenshots
  are compared with Pillow, else kept as `unavailable`. Only a temporary
  `/data/local/tmp` UI dump is written, then removed. `ok` means
  no failure; `unmeasured` lists unavailable checks.

## D. Physical phone (owner only)

Only the owner, or someone the owner asks, runs `runtime --physical-device`.
Report pass/fail facts and versions only.

## E. Signed outputs, failed-job cleanup and publication

Keep three records per run:
**source** (pinned main SHA and config at run start), **signed output** (the
signer's immutable, hash-bound result and receipt), **public/device** (the
pixel-ota release, then any phone). Use real runs, never a test release; Infra
supplies host listings (the verifier has no host access).

**Signer identity** — every signed output must equal the permanent identities;
any change fails (no regeneration):

| Device | App signer | OTA certificate (`releasekey.x509.pem` DER SHA-256) | AVB key (`avb_pkmd.bin` SHA-256) |
| --- | --- | --- | --- |
| frankel | `650d47f9…0bfb` | `2ce41f9e…268a` (`frankel.json` `identities`) | `7c19d7fa…8822` |
| rango | `650d47f9…0bfb` | the durable first-use record (`rango-identity/first-use.json`); must differ from frankel's | same record; must differ from frankel's |

Check the OTA package and payload signatures against that certificate and
vbmeta against that key (the release verifier's `checkOtaSignature`/`avbtool`
receipts), and the APKs with `apksigner`.

**Failed-job cleanup** — after a real failure and after success:

- the per-job workspace is gone (or quarantined with a receipt) on the signer;
- no key, keystore or passphrase file was ever on a build worker;
- the signing lock is released and never held a build worker's lock; record
  signing wait time per run;
- nothing partial is public: no draft left, feed line and Latest unchanged;
- a retry reuses the signed output byte-for-byte or re-signs with the same
  identity; one build number never has two public outputs.

**Publication** — per device and run:

- `verification.json` candidate equals the pinned main SHA (an ancestor of
  main); build number fresh and above every earlier one for that device;
- `SHA256SUMS` covers every asset and a fresh download re-hashes equal; OTA
  `pre-device` equals the device;
- frankel: tag `frankel-{build}`, Beta Latest moves only after verification and
  the download check, feed `frankel-stable` is `build timestamp frankel stable`;
- rango: tag `rango-{build}`, never Latest, feed classification `beta`, notes
  hash pinned; publishing rango leaves frankel Latest unchanged;
- no silent promotion to production;
- record source SHA, device, version, channel, artifact SHA-256 and elapsed
  time, then run A with that run's expectation.

Baseline: `rango-2026103001` (release 429262439, OTA `2613738b…1bbf`) is a
manual OTA publication; first install and phone acceptance are not shown.

## F. Factory installers (`{device}-install-{build}.zip`)

`scripts/factory-package.py` on delivered bytes (tiers: `docs/OS-FLAVORS.md`);
no downloads; no host or key reads.

1. **Pin:** `python3 -I scripts/factory-package.py contract --flavor F`
   (exit 0), then read `factorySigning`. A null `publicKey` fails
   `signatureVerified` (all three at `9f2c478`, where no job produces an
   installer). Never substitute the OTA certificate, AVB or adjacent keys.
2. **Classify:**

   ```sh
   python3 -I scripts/factory-package.py classify ARCHIVE --flavor F --build B \
     --target-files TF --target-files-observation OBS.json \
     --firmware-observation FW.json --otatools ZIP --otatools-sha256 H \
     --work-dir /scratch/factory [--signature ABS.sig] [--first-use-binding FU.json]
   ```

   - Only role `factory-install` can be ready (never an OTA or the generator's
     `{device}-factory-{build}.zip`).
   - `structurallyComplete`: exact members, byte-equal to the observed signed
     target-files; `avb_pkmd.bin` equals the AVB pin.
   - `contentVerified`: super, unpacked with the pinned otatools, equals the
     target-files images.
   - `signatureVerified`: `ssh-keygen -Y verify`, `allowed_signers` from the
     pin only, namespace `factory images`, over the classified bytes.
   - `factoryReady` needs all three with `missing` and `problems` empty
     (exit 0; 3 refused). Record both lists verbatim.

| Claim | Established by | Not established |
| --- | --- | --- |
| Signed images | Equality with the signed target-files; AVB pin; the release `avbtool` receipt (E) | Archive origin (`classify` reads vbmeta headers only) |
| Signed outer archive | `signatureVerified` | Image contents |
| Phone acceptance | Owner-run phone checks (D) | Anything `classify` reports (`phoneValidated: false`) |

Record each tier, the contract revision and the archive, signature, verifier
and otatools sha256; synthetic observations never count.

## Never claim

Runtime or visual results from inspection alone; Pixel results from
Cuttlefish or the reverse; acceptance from a heuristic or beyond what the
selected reference records; historical boots (`docs/upstream/`) as current;
one user's state for another; a candidate's identity from another candidate,
source or a planned version; production signing reliability from a fixture
pass; `factoryReady` from structure, a `.sig`'s presence or signed images;
phone results from `classify`.
