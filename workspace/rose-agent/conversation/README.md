# Conversation mode

Explicit prepare/start/end mode. Prepared meeting notes plus general project context are loaded into GPT-Live 1 at session startup. Questions covered by the briefing should be answered directly. Delegated requests use GPT-6.1 Sol with low reasoning and requested ultrafast tier. Served tier and time until backend reply are saved on each turn; actual speech latency is not yet measured.

The delegated backend is a separate Responses request with no general execution tools. Its structured output contains a reply, an optional notebook addition, and a narrow Start Work intent. Only validated notebook text is appended, and it is saved before a successful reply returns. It cannot browse, run arbitrary shell commands or control apps. The host handles the explicitly authorized cloud handoff separately and replaces model launch claims with the actual receipt. Unknown answers should be stated as unknown. A prompt alone is not a guarantee of grounded answers; evaluate the live model with covered and uncovered questions before relying on it.

Notes are in the private VM `conversation-notebooks.json`, outside source control. Entries and turns persist across restart, and stable turn IDs prevent duplicate writes. Preparation never activates the mode. Switching modes requires the current voice session and task to finish, so every new voice session receives the correct startup context. Controls are in Rose Agent's Server connection → Conversation mode. The authenticated endpoint is GET/POST `/conversation-mode` with actions prepare, start, end.

An explicit Start Work handoff submits the agreed action items to the configured destination. The notes model returns a structured handoff intent only for a new user authorization; the host performs submission and supplies the spoken result from its receipt. Ending a call or mode never starts work. For this cloud VM, configure the private `conversation-work.json` as `{"target":"vm","cwd":"/absolute/workspace"}`. This creates a new thread and turn through the persistent remote Codex daemon, using that daemon's configured account model. Pair ChatGPT with the VM to see those sessions. The voice task model selection is separate. A managed Codex Cloud build environment can alternatively use `{"target":"cloud","environmentId":"env_..."}`; its environment ID is distinct from a remote-control host ID. If neither destination is configured, Start Work reports that work has not started. Submission intent and any thread ID are persisted before the turn starts. Repeated commands reuse the existing handoff, and uncertain submissions are never retried automatically.

The normal task agent remains separate and is restored when this mode is ended. Initial prepared context is a dated snapshot. Progress updates are appended to the original notebook and loaded into later sessions; they do not silently rewrite the prepared briefing.

## Work and progress tools

`python3 rose-agent/conversation/control.py status` reads the current meeting ID, notebook, latest per-item statuses and any launch receipt.

On a new explicit authorization, the normal task agent can call `start-work --meeting-id ID --authorized --key STABLE_REQUEST_ID`. This is the same authenticated handoff the notes backend uses. It is not triggered by finding action items in historical context.

After each action item, the task agent must call `progress --meeting-id ID --item NUMBER --status completed|blocked|in_progress --summary 'Result' --evidence 'Verification and remaining work' --key STABLE_UPDATE_ID`. Save the update before reporting the item as completed. The authenticated endpoint also accepts `action: progress` with these fields. Status updates preserve the original meeting, append history, retain latest status per item and deduplicate retries. A `completed` status must describe the scope actually verified; do not call a phone connection completed merely because the VM daemon is online.

VM task prompts include the original meeting ID and the local progress command, requiring each item result to return to the same notebook before completion is reported. The remote daemon runs separately from Rose Agent so a voice server restart does not terminate its tasks. Install `pixel10-codex-remote.service` under systemd with the correct account home and workspace. The Unix WebSocket connection disables compression extensions for compatibility with the installed daemon. Managed Cloud task prompts also require per-item results, verification and blockers, but those tasks do not automatically have access to this VM's local notebook endpoint: the normal task agent must bring back their final results and write progress. Automatic managed Cloud completion polling is not implemented.

Tests: `node --test rose-agent/conversation/mode.test.mjs`. They verify model settings, no execution tools, durable/deduplicated notes, malformed-response behavior, and direct-live context preloading. Real API availability, spoken grounding, tier use, reconnect and response latency require live verification.
